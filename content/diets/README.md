# Diets

The Nutrition Plans the store sells, as data. One JSON file per diet in `plans/`, rendered to a branded A4 PDF by `render.js`. The PDF has a cover, a "Si ta përdorësh" page, one page per day and a shopping list per week. Spec and tickets: `.scratch/diet-plans/`.

Run these from this folder (`content/diets/`); from the repo root, prefix the paths with `content/diets/`.

```
node render.js plans/<plan>.json                  # every size: out/<plan>/<plan>-<gender>-<weight>kg.pdf
node render.js plans/<plan>.json --only m-80-90   # one size
node render.js plans/<plan>.json --png            # also one PNG per page of the reference size (m-80-90)
node render.js plans/<plan>.json --out <dir>      # write to <dir>/<plan>/ instead of out/<plan>/
node render.js plans/<plan>.json --dump           # each size's computed plan as JSON instead of a PDF
```

- `--out`: in a project thread, Claude renders with `--out /mnt/project-files/diet-plans/out` so the PDFs can be attached to a reply.
- `--dump`: writes `<plan>-<gender>-<weight>kg.json` per size, with every gram, count and total the PDF would print (rounded to 0.1). It needs no Playwright, and two runs give the same bytes, so diffing two dumps proves a change moved no number.

Needs Node, and Playwright for the PDFs. Claude's cloud sessions have a global Playwright, which `render.js` falls back to; elsewhere run `npm install` here once (`npm run render -- plans/<plan>.json` works too). The fonts are the theme's own (`themes/optimum-lift/assets/fonts/`), so the PDFs and the site share one copy.

## Files

| File | What it is |
| --- | --- |
| `foods.json` | The food table: Albanian name, group, kcal and macros per 100 g. The only place numbers come from. |
| `recipes/<recipe-key>.json` | One dish each, written once and named by many plans (format below). The file name is the **recipe key**. |
| `recipes/INDEX.md` | Every Recipe by slot, with kcal, macros, tags and the plans that use it. Generated by `catalogue.js`; never edit it. |
| `plans/*.json` | One diet each. Names Recipes, never writes a meal out, never holds calories. |
| `plans/djegie-yndyre.json` | The worked example (2 days). Copy it to start a new diet. |
| `sizes.json` | The genders and weight ranges every plan is built in, and how portions scale. |
| `style.css` | The look. Brand colours and fonts from the theme. |
| `photos/` | Dish photos, referenced from a Recipe's `photo` field. |
| `render.js` | The renderer. `package.json` pins its Playwright. |
| `catalogue.js` | Checks every Recipe and plan and writes `recipes/INDEX.md`. `--check` only compares. |
| `lib/recipes.js` | Loads and checks Recipes, and turns a plan's meals into full meals for the renderer. |
| `tests/` | Fixtures and `run.js` (`npm test`), the renderer's checks. |
| `out/<plan>/` | Rendered PDFs, one per size. Not committed. |

## Recipes

A **Recipe** is one dish: Foods with grams, steps and a swap, written once for the reference person (an 80 kg man). Plans name it by its key.

```json
{
  "name": "Omëletë me spinaq e djathë",
  "slots": ["breakfast"],
  "minutes": 10,
  "tags": ["vegetarian"],
  "photo": "",
  "ingredients": [
    { "food": "egg", "grams": 150 },
    { "food": "egg_white", "grams": 150 },
    { "food": "spinach", "grams": 60 },
    { "food": "white_cheese", "grams": 25 },
    { "food": "wholegrain_bread", "grams": 70 }
  ],
  "steps": ["Rrihi vezët bashkë me të bardhat.", "Kaurdis spinaqin 1 minutë në tigan pa vaj.", "Hidh vezët, thërrmo djathin sipër, mbuloje 3 minuta."],
  "swap": "Djathë i bardhë → gjizë, 40 g"
}
```

- **Key:** the file name, from the dish's name folded to ASCII (`ë→e`, `ç→c`), lowercase, words joined by hyphens. A key is never renamed or reused once a plan names it.
- `name` (unique), `slots` (one or more of `breakfast`, `snack`, `lunch`, `dinner`, `preworkout`), `minutes` (0–240), `ingredients` (1–10) and `steps` (1–4 short sentences) are required.
- `tags` come from a fixed list: `vegetarian`, `pescatarian`, `dairy-free`, `gluten-free`, `meal-prep` (keeps 3 days in the fridge), `balkan` (a local dish). Calories are never tags.
- An ingredient is `food` (a `foods.json` key) and `grams` (raw weight), plus optional `note` ("i papjekur"), `label` (printed instead of the Food's name) and `household` (printed when there are no grams). A Food appears once per Recipe. Spices are the exception: each `"food": "spice"` line has its own `label` and a `household` text, and no grams.
- Anything else in the file is an `ERROR`. So is an unknown Food or tag.

A plan's meal names a Recipe:

```json
{ "slot": "lunch", "time": "13:30", "recipe": "pule-ne-skare-oriz-e-sallate-shope", "grams": { "rice": 85 } }
```

- `portion` (0.5–2, default 1) multiplies every ingredient, and the grams in the swap.
- `grams` then sets a Food's grams for this plan only. `0` leaves the Food out of this meal. It cannot add a Food the Recipe does not have; that is a new Recipe.
- Using a Recipe in a slot it does not list is a `WARNING`.
- A swap's grams follow `portion` and the Size, but not `grams`: the renderer cannot tell which Food the swap replaces. Keep an override on the swapped Food within about 20% of the Recipe's grams, or the swap no longer matches; past that, write a new Recipe.

## Instructions for Claude filling a diet

1. **Read `recipes/INDEX.md` first.** Pick Recipes that fit by slot, tags and calories. A diet should mostly reuse Recipes; a new diet usually adds only a handful.
2. Copy `plans/djegie-yndyre.json` to `plans/<slug>.json`, where `<slug>` is the diet's name in lowercase with hyphens.
3. Fill `plan`: name, tagline, who it is for, water, and `goal` (`cutting`, `recomposition`, `bulking` or `maintenance`; a note for people, the renderer does not read it). Write the plan for an 80 kg man; the other sizes are generated. Write `how_to` (4–6 rules) and `adjust` (2–4 rules) for this diet specifically. A women-only diet sets `"sizes": { "genders": ["female"] }`.
4. Write 7 days for Java 1 unless the brief says otherwise. Four meals a day: a day page fits four meal cards. Use different meals across days; repeating a breakfast twice a week is fine. Training and rest days differ in carbs, not in protein.
5. Each meal is `slot`, `time` and `recipe`. Never write a meal out in a plan: the render refuses it.
6. **Fit calories in the plan, not in the Recipe.** Set `kcal_target` per day for the 80 kg man, then use `portion` and `grams` until the render reports every day of every size within 5%. Protein should be about 2 g per kg of the reference weight (so ~160 g at portion values, before Size scaling; the m-80-90 PDF prints about 5% more) on cutting and recomposition plans, 1.6–2 g on others.
7. **Write a new Recipe only when nothing in the index fits.** Name its key from the dish's name (see above), give it 3–6 ingredients, 2–3 short steps and one `swap` with grams that keep calories roughly equal, set its tags, then run `node catalogue.js`.
8. A Food that is missing from `foods.json`: add it with values per 100 g from USDA FoodData Central or CIQUAL, and say which in your summary. Never change an existing Food's numbers or rename its key.
9. **Changing an existing Recipe changes every plan in its "Used in" column.** Only do it when the change is right for all of them. Then re-render each of those plans and list for Brilant which Products need new PDFs. A change that suits one plan goes in that plan's `portion` or `grams`, or into a new Recipe.
10. Run `node catalogue.js`, then `node render.js plans/<slug>.json --png`. Look at every page of the reference size, check the smallest size (`--only f-50-60 --png`) too, and fix every `ERROR` and any `WARNING` (a day off target, a page too full, a Recipe in the wrong slot, an out-of-date index).
11. Write in Albanian, short sentences, informal "ti". Use local foods and dishes first.
12. **In a project thread**, render with `--out /mnt/project-files/diet-plans/out` and attach the PDFs from there. Commit the plan, any new Recipes, `foods.json` and `recipes/INDEX.md`; never the PDFs.
13. Hand back the PDFs and a short summary for Brilant: new Recipes, new Foods (with their source), changed Recipes and the plans they affect, and wording you are unsure of.

## Photos

Leave a Recipe's `photo` empty and the page shows a placeholder strip. To use a photo, put a JPG or PNG in `photos/` (landscape, at least 1200 px wide) and set `"photo": "photos/<file>.jpg"` on the Recipe; every plan that uses it then shows it. The photo strip grows a little and darkens at the bottom so the meal label stays readable.

Best: your own phone photos of the dishes on a plain plate. Second best: free stock photos from Unsplash or Pexels, whose licences allow commercial use without credit; check that the photo actually matches the recipe.

## Sizes: one plan, ten PDFs

A plan is written once, for a man of 80 kg (`reference_weight` in `sizes.json`). The renderer builds it in every size: Mashkull and Femër, each in 50–60, 60–70, 70–80, 80–90 and 90+ kg.

- Each size multiplies every portion by (middle of the weight range / 80) ^ 0.75, and by 0.88 for women. Calorie needs grow more slowly than body weight, so a 95 kg man gets about 14% more than the reference, not 19%.
- Portions are rounded to what a cook can measure: whole eggs, half slices of bread, half spoons, 5 g steps. Foods with a `unit` in `foods.json` are printed in pieces ("1½ fetë · 45 g").
- Rounding moves a day off its target, so each day is nudged back; the report warns if any size still ends more than 5% off.
- Grams in a `swap` text scale too.
- The cover says who the copy is for ("Përgatitur për ty: Femër · 50–60 kg"), and so does every page header.
- A women-only diet sets `"sizes": { "genders": ["female"] }` in its plan file, and can set its own `weights` too.

## Selling the sizes in WooCommerce

1. Make the diet Product a **Variable product**.
2. Under Attributes add **Gjinia** (Mashkull | Femër) and **Pesha** (50–60 kg | 60–70 kg | 70–80 kg | 80–90 kg | 90+ kg), both "Used for variations". A women-only diet gets only Pesha.
3. Under Variations choose "Generate variations", then use the bulk actions to toggle **Virtual** and **Downloadable** and set the price on all of them at once. Open each variation and attach its matching PDF.
4. To update a plan, re-render and replace each variation's file in the same slot.
